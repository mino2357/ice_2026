# 2026-11-24 VVT マップの探索器（`vtSearch`）から $J_0$ を取り除く

## 指示

外部のレビュー（ソースの点検の 3.2）の `vtSearch` の $J_0$ について，利用者が「$J_0$ を取り除く」と判断した（`docs/changes/2026-11-24-review-gemini-6.md` の「朝の判断」の 5）．

## 要件の差分

無い．`vtSearch` を使うのは VVT マップの最適点を詰める段（SPEC-34 B の 3）だけで，そこは $J_0$ を使わない．SPEC-34 にも $J_0$ は書かれていない．バルブタイミングの探索器（`vtQuad`．SPEC-32 C）の $J(\mathbf x_0)$ は画面の表で使うので変えない．

## 決めたこと

* `vtSearch` の最後で，探索の前の点 $\mathbf x_0$ を細かい許容で評価して $J_0$ として返していた部分（段階 `'x0'`）を消した．
* この評価は，勾配の段の最初（始点は $\mathbf x_0$）か，始点が無いときの代わりの評価で，同じ点・同じ許容の値がすでに覚えられている．そのため，機関を動かす評価は起きず，探索の進み方も結果も変わらない（コードを読んで判断し，下で確かめた）．

## 検証の結果

* **前後の比較**（Node.js．直す前のコミットの `vtSearch` と比べた）：解析的な関数 3 つ × 始点 4 つ × 評価の上限 5 通り（3，5，10，20，400．打ち切りを含む）× 制約 2 通りの 120 通りで，評価を求めた点の並び，結果の点と値，評価の回数，打ち切りの有無，評価の記録がすべて同じだった．
* 動きを変えない整理なので，新しい検査は足していない（直す前に FAIL する検査は作れない）．
* **段階 1**（`npm run verify`）：第25版とのビット比較は一致，全項目 663 件中 FAIL 0 件（TEST-34 の VVT マップを含む），組の失敗 0，所要 $533\ \text{s}$．性能の記録の上限超え（10 件）は段階 1 では判定せず，記録するだけ．
