テストは 1 フレームに $12\ \text{ms}$ だけ計算して次のフレームを待つ（`RUN.over`．画面が固まらないように）．計算に使えるのは最大で約 $72\%$（$12/16.7$）．予算だけを $200\ \text{ms}$ にした写しで，上位のテストを単独で実行して比べた．

* TEST-37 の行は出力に無かった（`--time` の集計の最後のテストが落ちる．道具の不具合の可能性．確かめていない）．

## 3. 全項目の中で実行すると遅くなる

同じテストを単独で実行したときと，全項目の中で実行したときで，所要が大きく違う．

| テスト | 単独 [s] | 全項目の中 [s] |
| :--- | ---: | ---: |
| TEST-32 | 63.6 | 90.0 |
| TEST-34 | 65.2 | 101.3 |
| TEST-26 | 59.4 | 69.2 |

* 全項目の中では $1.2$〜$1.6$ 倍遅い．前のテストが残したもの（メモリ，表，DOM，キャッシュ）による可能性がある（推定．原因は調べていない）．

## 4. 並列にしていない

* テストは 1 つのブラウザの 1 つのページで，順に 1 本で実行している．計算機は 4 コア 8 スレッドあるが，使っているのは 1 本だけ．
* `src/core.js` は DOM に依らないので，機関の計算だけの検査は Node.js でも動く（`tools/dev/bitcheck.js` はそうしている）．

## まとめ（推定を含む）

* 主な原因は，(1) 機関のサイクルを多数回す検査が多いこと（計算そのもの．1 サイクル約 $9\ \text{ms}$），(2) 1 コアで順に実行していること，(3) 全項目の中で後のテストほど遅くなること．(4) フレームごとの待ちは $10$〜$16\%$．
* (1) は本質的な計算量だが，(2) と (3) は進め方の問題で，変えられる．

## 5. 組に分けて同時に実行した結果（2026-11-24）

* 全項目を所要時間の実測で 4 組（各約 $214\ \text{s}$ の見込み）に分け，`run.js` を同時に 4 本実行：全部 PASS，壁時計 $440\ \text{s}$（1 本では $855\ \text{s}$．$1.94$ 倍速い）．計算機は 4 コア 8 スレッド．
* 段階 1 の全項目はこの形にした（`tools/dev/shard.js`）．性能の記録は同時の実行で値が変わるので，段階 1 では判定しない（今までどおり）．

## 6. 全項目の中で遅くなる原因（2026-11-24．朝の判断の 12 の (b)）

3 節の「全項目の中では 1.2〜1.6 倍遅い」の原因を，同じ計算機で，同時に別の重い処理を走らせずに測った．TEST-32（弁時期の最適化）の所要を，単独と，前に別のテストを 1 つだけ走らせたときで比べた（`node tools/dev/run.js --vp 360x640 --noperf --time --only …`）．

* 先に `run.js --time` の不具合を直した：最後のテストの所要を 20 ms ごとの見回りで締めていたので，結果を読むのが先になると最後のテストが落ちた（3 節の「TEST-37 の行が無い」もこれ）．`__done` が 1 になった時点で締めるようにした．

| 前に走らせたテスト | TEST-32 の所要 [s] |
| :--- | ---: |
| なし（単独） | 57.8 |
| TEST-11（動力計） | 54.1 |
| TEST-12（ECU） | 52.6 |
| TEST-16（解説タブ） | 58.2 |
| TEST-24（実測との比較） | 58.7 |
| TEST-29（化学平衡） | 58.5 |
| **TEST-13（数値積分）** | **117.2** |

* 遅くするのは TEST-13 だけ．ヒープは TEST-13 の後で約 37 MB で，シナリオの控え（`SC`）を空にして GC をしても TEST-32 は速くならなかった（$93.7$，$94.2$，$108.4\ \text{s}$）．メモリではない．
* TEST-13 を途中の検査の数で打ち切ってから TEST-32 を走らせた（二分）：34 個目まで 52〜65 s，35 個目（段の $\omega < 0$）まで 60.1 s，36 個目（有限でない結果を受け入れない．TEST-13 項目 27）まで 93.5 s．
* 項目 27 は，右辺の圧力の成分を NaN にしてステップを進める．Chromium の中で同じことをすると，その後の機関（既定，始動から 2 s）が 146 ms から 217 ms に遅くなり，戻らなかった．補助積分の成分を NaN にしても遅くならない．物性の表と統計（`GAS.stat`）は汚れていない．
* 原因：圧力が NaN の段で，既燃ガスの物性の補間（`burned`）の添字が NaN になり（範囲に丸める関数が NaN をそのまま通していた），配列を NaN の添字で読んだ．このため配列の読み出しの場所が遅い汎用の経路に変わり（JavaScript エンジンの最適化．推定），ページを開き直すまで戻らない．丸める関数が NaN を下端にする写しでは，同じ操作の後も遅くならなかった（$155 \to 142\ \text{ms}$）．
* 直した（REQ-13 の 19，TEST-29 項目 17．`docs/changes/2026-11-24-nan-index.md`）：TEST-13 の後の TEST-32 は $117.2 \to 63.2\ \text{s}$．
* アプリでも，計算が発散して止まった後にコールドリセットして続けると，同じく遅くなっていた（推定．項目 27 と同じ道筋）．
* Node.js（V8 の版が違う）では，この遅れは再現しなかった．
* 実機（Android，利用者の報告，版 `c62b261f`）は全 37 本で $204.5\ \text{s}$，TEST-32 が $22.4\ \text{s}$，TEST-13 の 1 サイクルの計算時間が $2.01\ \text{ms}$ で，開発用の計算機（$8$〜$12\ \text{ms}$）より約 4〜6 倍速い．段階 1 の性能の記録の上限超えの多くは，計算機の速さの差による（推定．同じ版を同じ計算機で比べてはいない）．
