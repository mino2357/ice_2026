### SPEC-20：検証の基盤（REQ-20）

#### A. 実行区分
| 区分 | 内容 | 実行の場所 |
| :--- | :--- | :--- |
| [A] 解析 | 関数・状態機械・恒等式の検査（すぐ終わる） | アプリ内 |
| [S] シナリオ | 下の表のシナリオで `EngineCore` を走らせる検査 | アプリ内 |
| [U] 画面 | DOM・Canvas・合成した Pointer Events による検査（現在のビューポートで） | アプリ内 |
| [D] 開発時 | 複数のビューポートでのヘッドレス検証 | 開発時 |
| [M] 実機目視 | 自動化できない見た目・操作感・聴感（要件定義書 5 節のチェックリスト） | 利用者の実機 |

#### B. 規則
1. TEST-01〜37 の [A][S][U] の項目はすべてアプリ内に実装し，`[全テスト実行]` で実行できる．チップの状態は「未実行／実行中／PASS／FAIL」の 4 つだけ．
2. **利用者の状態によらない**：設定画面・解説・画面の構成を操作する [U] の検査は，開始時に全設定を既定値，刻み ×1，保留なし，機関をコールドリセットした状態にしてから行い，終了後に実行前の状態（設定値，保留値，刻み，運転の状態，基準サイクル，表示中のページ）へ完全に戻す．
3. [S] は運転中の機関とは別の `EngineCore` で実行し，運転中の機関の状態と設定を変えない．
4. テストの実行中も画面が固まらないよう，1 フレームあたり $12\ \text{ms}$ 以内に分けて実行し（積分のループでは 4 ステップごとに経過時間を調べる），進捗を表示する．途中で中止できる．実行中は運転中の機関の時間の進行を止めてよい（状態は保つ）．
5. 全テストの所要時間は $480\ \text{s}$ 以内．
6. 決定性：シナリオはサイクル変動 OFF で回し，乱数は種を固定した擬似乱数だけを使う．同じビルドで 2 回実行した結果の数値が完全に一致する．
7. 各検証項目は，項目名・基準・実測値・誤差・合否を持ち，詳細カードに表示する．数値の項目の誤差は $\frac{\lvert\text{実測} - \text{基準}\rvert}{\max(\lvert\text{基準}\rvert,\ s)}$ とする．$s$ はその量の大きさの尺度で，基準が差（BMEP $=$ IMEP $-$ FMEP $-$ AMEP など）で $0$ に近くなりうる項目で与える（基準が小さいと相対誤差が跳び，正しい計算でも FAIL になるため．外部のレビューの指摘）．与えない項目は $s = 0$ で，基準が $0$ のときは分母を $1$ とする．
8. **納品条件**：要件定義書 5.1 節．機能の検査（[A][S][U]）に 1 件でも FAIL があれば成果物を公開しない．[M] で見つかった不具合は，再発を防ぐ自動テストを加えてから直す．
9. **画面のモード**（開発時検証の 5 通りで使う．9 節）：[A] と [S] の項目は画面の大きさによらず同じ値になる（6 の決定性）ので，ビューポートごとに繰り返さない．画面のモードでは，[U] の項目を持つテスト（TEST-15〜23，25〜27，30〜35）だけを実行する．そのうち TEST-17，20，21，25〜27，30，32〜35 では [U] の項目だけを実行し（[U] の項目が使うシナリオは走らせる），TEST-20 では項目 2，3，5 を実行する．TEST-15，16，18，19，22，23，31 は全項目を実行する（[A][S] の項目は短い）．結果の表示は「PASS $n$/17（画面のモード）」の形にする．アプリの `[全テスト実行]` は常に全項目を実行する（`runAll(null, 1)` で画面のモード）．
10. **性能の記録**：実時間（壁時計）を測って上限と比べる検査は，機能の検査と分けて「性能の記録」として持つ（下の表の 25 件．検査の名前の先頭に「［性能］」を付ける）．測った値は，実行する計算機の速さと，ブラウザのガベージコレクションの停止で変わるので，機能の合否と混ぜない．
    * 判定する実行（アプリの `[全テスト実行]`，段階 2 の `npm test`）では，上限を超えると FAIL にする．判定しない実行（段階 1 の `npm run verify`）では，値と「上限超え」の印を記録するだけで FAIL にしない．
    * 結果の要約に「性能の記録 n 件（上限超え m 件）」を表示する．詳細カードは，上限を超えた記録を「FAIL（上限超え）」か「上限超え（判定しない）」と表示する．
    * `npm test` の終了コードは，すべて PASS で 0，機能の検査に FAIL か実行時の誤りがあれば 1，機能はすべて PASS で性能の記録だけが上限を超えたとき 2．
    * テスト項目（TEST-nn）の文の中の実時間の上限は，すべてこの表の記録として扱う．シミュレーションの時間で測るもの（完爆までの時間など）と，模擬の機関で打ち切りの動作を確かめるもの（TEST-15，TEST-26 の「1 ステップが 10 ms かかる模擬」など）は，計算機の速さによらないので機能の検査である．

11. **結果のテキスト**（REQ-20 の 7）：検証タブの `[結果をコピー]`（`[全テスト実行]` の右．結果が無いときと実行中は無効）は，次の行を改行でつないだテキストを作る．
    * 「SI機関シミュレータ 検証の結果」，「ビルド：」ビルドの ID，「日時：」実行を始めた時刻（ISO 8601，UTC），「環境：」ユーザーエージェント．
    * 環境の 2 行目：プラットフォームと機種（ブラウザが `navigator.userAgentData` で教えるときだけ），画面の大きさ，表示領域の大きさ（CSS px），画素の比，論理コア数，メモリ（ブラウザが教えるときだけ），言語，数式の組版の状態．
    * 「要約：」PASS の数，検証項目と FAIL の件数，所要時間，性能の記録の件数と上限超えの件数，最長フレーム間隔．
    * テストごとに 1 行：番号，合否，検査の数，所要時間 [s]，テストの名前．
    * 「FAIL と上限超え：」の後に，該当する検査を 1 行ずつ（番号，FAIL か上限超えか，検査の名前，基準，実測）．無ければ「なし」．
    * 「性能の記録（実測｜上限）：」の後に，性能の記録を全件 1 行ずつ．
    * **ビルドの ID** は，成果物の内容（ID を入れる前の HTML）の SHA-1 の先頭 8 桁（16 進）で，ビルドのときに入れる．ソースと文書が同じなら同じ ID になる．
    * **コピー**：`navigator.clipboard.writeText` で書く．書けなければ `document.execCommand('copy')` を試す．どちらもできなければ，詳細カードの中に，同じテキストを入れた読み取り専用の枠（全体を選択した状態）を表示し，利用者が選んでコピーできるようにする．書けたときはボタンの文字を 1.5 s の間「コピーしました」に，枠を出したときは 4 s の間「枠からコピー」にする．
    * 機種の名前（Galaxy S26+ など）は，ブラウザが教えないことが多い（Android の Chrome は機種を伏せ，iPad は Mac と名乗ることがある）．テキストに無ければ，貼るときに利用者が書き足す．
12. **共有の値の復元**（REQ-20 の 8）：テストが一時的に書き換える共有の値は，管の摩擦係数と入口損失係数（TEST-25，27），時計（TEST-15），クリップボードとコピーの命令（TEST-15，TEST-20），物性の表の作成（TEST-26），振動の機能とページが非表示かどうかの値 `document.hidden`（TEST-36）である．書き換えるテストは，戻し方を登録するか（`onEnd`），`try`／`finally` で戻す．全テストの実行は，各テストについて，終わったとき，途中で中止されたとき，例外で止まったときのどれでも，止まっている generator を終わらせて `finally` を走らせ（`genStop`），登録された復元を新しいものから順に実行する（`endAll`）．

#### C. シナリオ
既定設定から，サイクル変動を OFF，回転数の制御をスロットル制御にして（どちらも設定の既定と同じとは限らないので明示する．回転数の制御の既定は動力計制御），DOPRI5（第26版までの既定の解法）で積分する（テストの判定値は DOPRI5 で求めたもの．今の既定の BS3 の精度は，TEST-13 項目 14〜21 で DOPRI5 の参照解と比べて確かめる）．「継続」は元のシナリオの終端の状態を複製して続ける．

| S2（アイドル） | S1 を継続 | なし | $+15\ \text{s}$ |

回転数を固定した全開の定常（SPEC-26 の計測と同じ条件）は，`EngineCore` の回転数の固定（SPEC-10）と壁温の固定（$360\ \text{K}$）を使う．
